# 2026-W01 周报｜chat-api（Day1–Day7）

## 1) 本周交付（面试一句话版本）
我用 FastAPI 从 0 到 1 搭了一个可运行、可测试、可替换引擎的聊天服务：支持 `/health`、同步 `/chat`、SSE 流式 `/chat/stream`，并实现 mock/ollama 双 provider、trace_id 链路追踪、SSE 事件标准化与回归测试。  

> 7 天主线：环境与服务跑通 → 路由与中间件 → 可插拔引擎（mock/ollama）→ README+测试 → SSE → SSE 标准化增强 → 同步接口对齐 + 契约测试。

## 2) 本周功能清单（按模块，不按天）
> 对应你 7 天游记的内容：Day1 环境/服务；Day2 路由/中间件；Day3 引擎与 Ollama；Day4 README+测试；Day5 SSE；Day6 SSE 标准化；Day7 配置与契约测试。fileciteturn9file1L3-L9

### API 层
- `GET /health`：健康检查（用于“服务活着/可接流量”）
- `POST /chat`：同步聊天（provider=mock|ollama），响应包含 `metadata(provider/model/latency_ms)`
- `POST /chat/stream`：SSE 流式聊天（provider=mock|ollama）

### LLM 引擎层（可插拔）
- `LLMEngine` 抽象：`generate()` / `stream()`
- `mock`：用于稳定跑通流程与测试
- `ollama`：真实调用本地（Windows）Ollama 服务与模型

### SSE 标准化
- `event: meta`（初始化：trace_id/provider）
- `event: token`（逐段输出）
- `event: usage`（统计：trace_id/provider/model/latency_ms/token_events）
- `event: done`（结束）
- `event: error`（结构化错误 JSON）

### 工程化
- README：快速启动、环境变量、调用示例
- pytest：健康检查、mock chat、SSE 事件、usage、错误分支
- 契约测试（contract test）：锁住 `/chat` 对外字段（trace_id/answer/metadata...）

## 3) 本周「面试自测卡片」（集中复习用）
> 用法：每天只写“做了啥+怎么验收”；所有面试点集中放在周报里，每周滚动更新。

### 卡片 1：为什么要做 mock provider？
- **Q**：你为啥先做 mock，不直接接大模型？
- **A**：先把“接口契约/流程/测试”跑通，隔离外部依赖，避免把问题混在一起（网络/模型/权限/超时）。
- **追问 1**：怎么保证 mock 不会和真实实现越来越偏？
  - **答**：用契约测试锁住对外响应结构；用集成测试覆盖关键分支（成功/超时/不可达）。
- **追问 2**：mock 应该模拟到什么程度？
  - **答**：模拟“行为边界”（同步返回、流式分片、错误事件/超时），不追求语义正确。

### 卡片 2：trace_id 的意义？
- **Q**：`x-trace-id`/trace_id 有什么用？
- **A**：把一次请求贯穿日志、响应、错误与统计，线上排障能“按一次调用定位问题”。
- **追问 1**：trace_id 从哪来？
  - **答**：中间件生成或从请求头读取，统一写回响应头与 body。
- **追问 2**：为什么放在 header？
  - **答**：网关/前端更容易拿到并记录；日志系统也更容易关联。

### 卡片 3：SSE vs 普通 JSON 响应差异？
- **Q**：为什么流式不用普通 JSON？
- **A**：JSON 是一次性返回；SSE 建立连接后按事件持续推送 token/usage/error，体验更像“打字机”。
- **追问 1**：为什么 SSE 出错时可能还是 HTTP 200？
  - **答**：连接已建立，业务错误通过 `event:error` 传递（通道层与业务层分离）。
- **追问 2**：前端怎么消费？
  - **答**：按 event type 分流：meta 初始化、token 拼接、usage 展示统计、done 收尾、error 弹错。

### 卡片 4：为什么要有 usage 事件？
- **Q**：你为啥要推 `event: usage`？
- **A**：可观测性：统一统计 provider/model/latency/token_events，便于对比不同模型、定位性能瓶颈。
- **追问 1**：token_events 是 tokenizer 的 token 数吗？
  - **答**：不是；这是“输出分片/事件次数”，用于衡量流式输出粒度与性能。
- **追问 2**：还可以加哪些指标？
  - **答**：prompt_tokens/completion_tokens、缓存命中、下游重试次数、队列等待时间等。

### 卡片 5：为什么同步 `/chat` 也要 metadata？
- **Q**：为啥 `/chat` 也返回 metadata，不只在 stream 里做 usage？
- **A**：对齐 sync/stream 两条链路的统计口径，前端与日志分析更统一，调优更方便。
- **追问 1**：mock 的 model 为啥是 null？
  - **答**：mock 不对应真实模型，但保留字段能简化前端与统计代码（统一结构）。
- **追问 2**：metadata 里放 trace_id 合理吗？
  - **答**：trace_id 已在顶层字段/响应头，metadata 里通常不重复，保持语义清晰。

### 卡片 6：为什么 settings 要动态读 env（property）？
- **Q**：你为啥不在 import 时读 env，而用 property 动态读取？
- **A**：避免“导入即固化配置”的坑；测试里 monkeypatch/setenv 立刻生效；运行时覆盖更自然。
- **追问 1**：那会不会每次调用都 getenv，影响性能？
  - **答**：配置读取成本极低；真要极致可在启动时缓存，或只对高频字段做缓存。
- **追问 2**：生产环境怎么管理这些 env？
  - **答**：容器/CI/CD 注入，或配置中心；关键是配置来源单一、可追踪、可回滚。

### 卡片 7：什么是契约测试（contract test）？
- **Q**：契约测试和单元测试有什么区别？
- **A**：单测测内部逻辑；契约测试锁“对外承诺”（响应字段/类型/语义），防止重构把接口悄悄改坏。
- **追问 1**：契约要锁到多细？
  - **答**：锁关键字段与语义（trace_id/answer/metadata...），不锁易扩展字段，留演进空间。
- **追问 2**：契约测试失败说明什么？
  - **答**：对外接口被破坏，属于高优先级回归，必须修或明确做版本升级。

### 卡片 8：为什么 Day4 就要引入 pytest？
- **Q**：这么小的项目，为啥这么早加测试？
- **A**：它是“快迭代”的保险丝：后面 SSE/引擎/配置改动很多，没有测试就会反复踩回归。
- **追问 1**：你优先测什么？
  - **答**：先测“最稳定的契约”：/health、/chat mock；再测 stream 的事件格式与关键事件（usage/error）。
- **追问 2**：怎么测 SSE？
  - **答**：断言 content-type 为 `text/event-stream`，并检查事件序列包含 meta/token/usage/done 或 error。

### 卡片 9：RAG 一句话解释（关联你之前自测题）
- **Q**：一句话解释 RAG？
- **A**：RAG=检索增强生成：先从外部知识库检索证据，再让模型基于证据回答，降低幻觉、知识可更新。
- **追问 1**：chunk 怎么切？
  - **答**：按语义段落/固定长度+重叠；以召回率与最终 QA 指标回归调参。
- **追问 2**：为什么 RAG 不是“塞更长上下文”？
  - **答**：长上下文成本高且易稀释注意力；检索拿“最相关少量证据”更便宜可控。
